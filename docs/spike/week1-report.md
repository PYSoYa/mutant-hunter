# MutantHunter 1주차 기술 스파이크 결과

**결론: GO.** 중단 기준(수동 킬 레이트 30% 미만)을 크게 상회함.

## 실험 설계

| 항목 | 값 |
|---|---|
| 대상 repo | `pysoya-agent-company` (Next.js 16 / TS / vitest 4) |
| 대상 파일 | `lib/llm/jsonGuard.ts` (154줄, DB 비의존 순수 로직) |
| 뮤테이션 도구 | StrykerJS + vitest-runner, `coverageAnalysis: perTest` |

원본을 건드리지 않기 위해 스크래치패드 복사본에서 수행. 베이스라인 전체 스위트 149 테스트 / 15초.

## Q1. 뮤테이션 테스팅이 CI에서 감당 가능한가 → **예**

| 측정 | 값 |
|---|---|
| 1개 파일(154줄) 뮤턴트 수 | 109 |
| Stryker 실행 시간 | **4~6초** |
| 뮤턴트당 평균 실행 테스트 | 1.9~2.0개 |
| 뮤테이션 전용 테스트 서브셋 실행 | 0.2초 (전체 스위트는 15초) |

목표였던 "5분 이내"를 압도적으로 충족. 단, 이는 **테스트 서브셋을 따로 구성했기 때문**임 — 원본 `vitest.config.ts`는 `globalSetup`으로 DB를 세우고 `fileParallelism: false`라 그대로 쓰면 훨씬 느려진다. 제품에서는 "대상 파일을 커버하는 테스트만 실행하는 설정"을 자동 생성해야 한다. (2주차 작업으로 편입)

## Q2. 살아남은 뮤턴트를 죽이는 테스트를 써낼 수 있는가 → **예 (88%)**

| 단계 | 뮤테이션 스코어 | 생존 |
|---|---|---|
| 기존 테스트만 | 57.80% | 36 |
| 생성 테스트 9개 추가 후 | **87.16%** | 8 |

- 겨냥한 비문자열 생존 뮤턴트 **24개 중 21개 킬 = 88%**
- 등가 뮤턴트 2개 제외 시 실질 **21/22 = 95%**
- 4개 게이트 전부 통과: 원본에서 통과 / 뮤턴트를 죽임 / 안정적 / 기존 158 테스트 무해

### 실제로 발견된 진짜 갭

기존 테스트가 왜 이걸 놓쳤는지가 흥미롭다:

1. **문자열 내 중괄호 처리** — 기존 테스트는 `"}{"` 처럼 **균형 잡힌 쌍**을 넣어서, `inString` 추적을 통째로 없애도 깊이 계산이 상쇄되어 통과했다. 여는 중괄호만 넣자 즉시 드러남.
2. **이스케이프 처리** — 기존 이스케이프 테스트는 입력이 직접 파싱에 성공해서 **스캐너 코드를 아예 타지 않았다.** prose로 감싸자 드러남.
3. **`formatZodError` 전체** — 오류 메시지 내용을 아무도 단언하지 않아 함수 전체가 미검증.

## 예상보다 중요했던 발견 3가지

### 1. StringLiteral 뮤턴트는 대부분 노이즈
생존 36개 중 **12개(33%)가 StringLiteral** — 대부분 LLM 프롬프트 텍스트(`REPAIR_SYSTEM = ""`). 프롬프트 문구를 테스트로 고정하는 건 유해하다. → **`excludedMutations: ["StringLiteral"]` 기본값**으로 두고, LLM 호출 전에 필터링해서 쿼터를 아낀다.

### 2. 등가 뮤턴트는 실재하고 영원히 안 죽는다
- `raw.trim()` → `raw`: `JSON.parse`가 공백을 허용하고 인덱스가 자기일관적이라 동작 동일.
- `i < length` → `i <= length`: `trimmed[length]`가 `undefined`라 어느 분기도 안 타고 루프 종료.

둘 다 **원리적으로 킬 불가**. 무한 재시도하면 쿼터만 태운다. → **뮤턴트당 재시도 상한 2회 + 등가 의심 목록 캐싱** 필요.

### 3. 검증 게이트가 실제로 오탐을 잡아냈다 ⭐
`tryParse`의 오류 반환을 겨냥한 테스트를 썼는데, 단언을 `/Failed to parse balanced JSON block: \S+/`로 느슨하게 쓰는 바람에 **뮤턴트가 만든 `"...block: undefined"` 문자열도 매칭되어 통과**해 버렸다. 테스트는 원본에서 멀쩡히 통과했고 리뷰로는 걸러내기 어렵다. **오직 "뮤턴트에서 실패하는가" 게이트만이 이걸 잡았다.**

이 프로젝트의 존재 이유를 스파이크가 스스로 증명한 셈. README 첫 페이지에 그대로 쓸 사례.

## 정직한 한계

- **생성기가 무료 티어 모델이 아니었다.** 이번 88%는 상위 모델 기준의 상한선이다. Gemini Flash 무료 티어 실측은 6주차 필수 과제이며, 여기서 크게 떨어지면 "테스트 생성" 대신 "뮤턴트를 리스크 설명으로 번역"으로 축을 트는 대안이 여전히 유효하다.
- 표본이 **repo 1개 / 파일 1개**다. 5주차 골든 코퍼스 전까지 이 수치를 일반화하면 안 된다.
- 대상이 DB 비의존 순수 로직이었다. I/O가 얽힌 모듈에서는 킬 레이트와 flaky 비율이 모두 나빠질 것으로 예상.
