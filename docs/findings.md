# 측정 기록

10주 동안 이 도구를 만들며 **측정한 것과 그때마다 틀린 것**을 남긴다.
결론만 적으면 왜 그 결론에 도달했는지가 사라지고, 같은 실수를 다시 한다.

전체 평가 결과 데이터는 [`docs/eval/`](./eval/)에 있다.

### 게이트는 실제로 작동한다

같은 뮤턴트(`ch === '"'` → `false`)에 두 가지 테스트를 넣고 돌린 결과다.

```
── killing.test.ts
   ✅ passes-on-original   통과
   ✅ kills-mutant         뮤턴트를 죽였다
   ✅ stable               3회 반복 통과
   ✅ suite-intact         기존 스위트 통과
   → 채택

── loose.test.ts
   ✅ passes-on-original   통과
   ❌ kills-mutant         뮤턴트가 살아남았다 — 결함을 잡지 못하는 테스트
   → 폐기 (kills-mutant)
```

`loose.test.ts`는 같은 함수를 테스트하고 원본에서 멀쩡히 통과한다. 리뷰로는
걸러내기 어렵다. 스캐너 경로를 타지 않아 결함을 못 잡는다는 사실은
**뮤턴트를 실제로 적용해 돌려봐야만** 드러난다.

재현: `npx tsx scripts/demo-gates.ts --repo <대상> --mutant-id <id>`

### 게이트는 실전에서 실제로 걸러낸다

미스트랄로 표본 3개(뮤턴트 1756개)에 24개 뮤턴트를 시도한 결과다.

| | |
|---|---|
| 시도 | 24 |
| 채택 | 6 |
| **채택률** | **25%** |
| 게이트 폐기 | **18** |

폐기 내역:

| 게이트 | 건수 | 무엇을 막았나 |
|---|---|---|
| `passes-on-original` | 10 | 생성된 테스트가 아예 깨짐 (`expected 'false' to be ''`) |
| `kills-mutant` | 8 | 원본에선 통과했지만 뮤턴트를 못 죽임 |

**`kills-mutant` 8건이 이 프로젝트의 존재 이유다.** 이것들은 원본 코드에서
멀쩡히 통과하는, 그럴듯해 보이는 테스트다. 코드 리뷰로는 걸러내기 어렵고
커버리지도 올라간다. 결함을 못 잡는다는 사실은 뮤턴트를 실제로 적용해
돌려봐야만 드러난다.

게이트가 없었다면 이 18건이 전부 PR 코멘트로 나갔을 것이다.

전수로 세면 안전망은 더 크다. 같은 표본에서 게이트는 **35번** 떨어뜨렸고
(`kills-mutant` 22 / `passes-on-original` 13), 그중 1건만 재시도로 살아났다.
최종 폐기 17건만 세면 안전망 크기를 절반 이하로 축소해 보고하게 된다.

**작은 표본의 숫자를 믿으면 안 된다는 교훈도 같이 얻었다.** 뮤턴트 2개짜리
표본에서는 채택률이 100%였다. 24개로 늘리자 25%가 됐다.

### 코멘트는 도구 용어 없이 읽혀야 한다

```
**L54** — 옵셔널 체이닝이 **사라져도**(값이 없을 때 터지게 되어도)
**어떤 테스트도 실패하지 않습니다.**
```

`- ch === '"'` / `+ false` 를 보고 왜 문제인지 알려면 뮤테이션 테스팅을
알아야 한다. PR을 읽는 사람 대부분은 모른다. "뮤턴트", "Stryker" 같은
말은 코멘트에서 완전히 뺐고 테스트로 강제한다.

코멘트는 PR당 하나만 유지하고 갱신한다. 커밋마다 새로 달면 알림 피로로
도구가 죽는다.

### 실제 출력을 렌더링해 보고 찾은 것

코멘트를 눈으로 확인하니 생성된 테스트가 160줄이었다. 모델이 **기존 테스트
파일(147줄/21개)을 통째로 베끼고 케이스 하나만 더하고** 있었다. 적용하면
같은 테스트가 두 번 돈다.

프롬프트에 복사 금지를 넣자 최대 길이가 50줄로 줄었다. 대신 채택률이
29.2% → 20.8%로 내려갔다.

**이 교환은 받아들인다.** 160줄짜리 중복 테스트는 채택돼도 쓸 수 없다.
채택률은 "쓸 수 있는 제안"을 세는 지표여야 하므로, 29.2%가 부풀려진
숫자였고 20.8%가 더 정직하다.

### 프롬프트 수정은 효과를 입증하지 못했다

관찰된 실패 패턴(기대값 오판)에 맞춰 프롬프트를 고치고 같은 표본·같은
provider로 A/B를 돌렸다.

| 지표 | v1 | v2 |
|---|---|---|
| 채택 | 6 / 24 | 7 / 24 |
| 채택률 | 25.0% | 29.2% |
| LLM 호출 | 45 | 42 |

**24개 중 1개 차이는 노이즈 범위다.** 채택률 +4.2%p는 그럴듯해 보이지만
실체는 뮤턴트 하나가 더 통과한 것뿐이고, 이것으로 개선을 주장할 수 없다.
효과를 판정하려면 반복 실행으로 잡음 폭을 먼저 재야 한다.

하네스는 제 역할을 했다 — 회귀를 막았고, 동시에 성급한 승리 선언도 막았다.

### 잡음 폭을 재고 나니 A/B 판정이 뒤집혔다

같은 조건(프롬프트 v3, 같은 모델, 같은 표본)으로 4회 관측했다.

| 실행 | 채택 | 채택률 |
|---|---|---|
| 1 | 5 / 24 | 20.83% |
| 2 | 7 / 24 | 29.17% |
| 3 | 6 / 24 | 25.00% |
| 4 | 6 / 24 | 25.00% |

**아무것도 바꾸지 않았는데 채택 수가 5~7로 흔들렸다. 범위 8.33%p.**

이 폭을 앞선 판정에 적용하면:

| 비교 | 변화 | 판정 |
|---|---|---|
| v1 → v2 | +4.17%p | 노이즈 |
| v2 → v3 | −8.33%p | **판정 불가** |

하네스가 "회귀"로 띄웠던 −8.33%p는 같은 조건에서 관측된 흔들림 폭과
같다. 회귀였다고 말할 수 없다. "복사 금지 때문에 채택률이 떨어졌다"는
설명도 근거가 없었다 — 그냥 흔들렸을 수 있다.

(복사 금지 자체는 유지한다. 160줄 → 50줄은 4회 관측 모두에서 일관됐고,
채택률과 무관한 별개 지표다.)

### 표본을 102개로 키운 결과

| | 24개 표본 | 102개 표본 |
|---|---|---|
| 채택 | 6 / 24 | 27 / 102 |
| 채택률 | 25.0% | 26.5% |
| API 호출 | 44 | 184 |
| 게이트 폐기 (전수) | 39 | 157 |

뮤턴트 1건이 4.17%p에서 **0.98%p**로 줄었다. 이제 2~3%p 효과도 볼 수 있다.

**가장 중요한 발견은 채택률이 아니라 표본별 편차다.**

| 표본 | 채택률 | 코드 성격 |
|---|---|---|
| `self-week3-gates` | 12.5% | 파일 I/O·프로세스 실행이 얽힌 배선 |
| `self-week4-action` | 15.0% | Actions 배관, 환경변수 |
| `self-week2-scanner` | **36.2%** | diff 파싱 — 순수 함수, 경계 조건 |

**12.5% 대 36.2%, 거의 3배.** 프롬프트를 만지며 쫓던 ±4%p는 이 차이 앞에서
무의미하다. 이 도구는 순수 로직에서 잘 듣고 I/O 배선에서는 약하다.

### 잘 테스트된 repo에서는 제안할 것이 없다 — 그게 올바른 동작이다

외부 OSS repo 두 곳에 돌린 결과다.

| repo | 뮤테이션 스코어 | 후보 | 채택 |
|---|---|---|---|
| `unjs/ufo` | 88.46% | 3 | 0 |
| `unjs/destr` | 86.11% | 7 | 0 |

둘 다 모범적으로 테스트된 코드다. 남은 뮤턴트는 **어려운 잔여물**뿐이고,
우리 도구는 그것들을 죽이는 테스트를 만들지 못했다.

**이때 침묵하는 것이 올바른 동작이다.** 증명하지 못한 것을 제안하면
메인테이너의 시간을 뺏고 도구의 신뢰를 한 번에 잃는다. `ufo`의 3건은
전부 게이트에서 걸러졌는데, 그중 2건은 아무 결함도 잡지 못하는
테스트였다. 게이트가 없었다면 남의 PR에 그대로 나갔을 것이다.

이 도구의 값어치는 **테스트가 얇은 코드**에 있다. 그것을 외부 repo에서
확인했다.

| repo | 뮤테이션 스코어 | 후보 | 채택 |
|---|---|---|---|
| `unjs/ufo` | 88.46% | 3 | 0 |
| `unjs/destr` | 86.11% | 7 | 0 |
| **`antfu/utils`** | **0.00%** | 7 | **6** |

`antfu/utils`의 `objectOmit`은 테스트가 하나도 없는 함수였고, 생성된
5개 케이스가 `omitUndefined` 분기 양쪽을 덮으며 4개 게이트를 모두 통과했다.
같은 도구가 88% repo에서는 0건, 0% repo에서는 6건을 낸다. **대상이
프롬프트보다 훨씬 크게 좌우한다**는 자체 측정(12.5% 대 36.2%)과 같은 방향이다.

### 외부 검증이 잡아낸 것 — 자체 repo에서는 가려져 있던 버그 3건

채택은 0건이었지만, 남의 코드에 처음 돌리자 우리 버그가 드러났다.

| 버그 | 증상 |
|---|---|
| CLI가 `MH_PROVIDER`를 무시 | Action과 CLI의 provider 선택이 갈렸다 |
| import 경로를 LLM에게 추측시킴 | 7건 중 6건이 `Cannot find module`로 사망 |
| 형제 테스트 탐색 실패 | `describe is not defined` |

두 번째가 특히 뼈아프다. 파일을 어디 놓을지도, 소스가 어디 있는지도
**우리가 아는데** "형제 테스트 스타일을 따르라"고 부탁만 하고 있었다.
결정론적으로 알 수 있는 것을 LLM에게 추측시키지 않는다.

세 번째는 `destr`의 `test/index.test.ts`가 소스를 `from "../src"`로
import해서 파일에 `index`라는 문자열이 하나도 없던 경우다. 파일명 일치를
강한 신호로 추가하고, 형제를 못 찾아도 repo 전체에서 러너 import 관례를
감지하게 했다.

수정 전후 실패 프로필:

```
수정 전:  import 6,  missing-api 10   ← 우리 버그
수정 후:  not-killed 9, assertion 5   ← 실제 능력 한계
```

**우리 버그가 사라지고 진짜 한계만 남았다.** 이 전환이 외부 검증의 값이다.

### 측정 장치의 분해능

뮤턴트 24개 표본에서 **1건 = 4.17%p**다. ±1건만 흔들려도 4%p가 움직이니
이 장치로는 8%p 미만의 변화를 판정할 수 없다.

프롬프트 개선이 5%p 효과를 낸다 해도 지금 설계로는 영원히 못 본다.
잡음은 대략 √n에 반비례하므로 2%p까지 낮추려면 뮤턴트를 100개 규모로
늘려야 한다. **무료 티어 쿼터가 이 프로젝트의 진짜 제약인 이유다.**

### 무료 티어 모델 첫 실측

`gemini-flash-latest`(Gemini 무료 티어)로 `jsonGuard-scanner` 표본을 돌린 결과다.

| | 시도 | 채택 | 채택률 | 폐기 |
|---|---|---|---|---|
| 재시도 수정 전 | 5 | 3 | 60% | `llm-error` 2 |
| 재시도 수정 후 | 5 | 4 | **80%** | `llm-error` 1 |

**주의해서 읽어야 한다.** 지금까지 실제 실행에서 발생한 폐기는 **전부 쿼터 오류**이고,
게이트가 떨어뜨린 테스트는 **한 건도 없다.** 응답을 받은 뮤턴트는 전부 채택됐다.

표본이 결론을 내기에 턱없이 작고, 게이트의 안전망 효과는 아직 합성 데모에서만
관찰됐다.

### 무료 티어 쿼터가 진짜 병목이다

Gemini 무료 티어는 모델당 요청 20회에서 막힌다. 6주차 실측에서 Gemini는
쿼터 소진으로 생성을 완주하지 못했고, 같은 표본에 미스트라를 붙이니
2개 뮤턴트를 34초에 2/2 채택했다.

**이것은 모델 품질 비교가 아니다.** Gemini는 품질로 떨어진 게 아니라 쿼터로
막혔다. 공정한 비교는 두 provider 모두 쿼터가 넉넉한 상태에서 같은 표본을
돌려야 하며, 그때는 리포트가 provider 교체를 경고로 표시한다.

미스트랄이 생성한 테스트의 실제 예 — `last?.rejectedAt` → `last.rejectedAt`
뮤턴트를 겨냥해 `attempts: []`로 `last`를 undefined로 만들어 TypeError를
유발한다. 원본에서 통과하고 뮤턴트에서 실패하는 정확한 킬이다.

### 왜 "줄"이 아니라 "선언" 단위인가

변경된 줄만 뮤테이션하면 그 줄을 감싸는 분기 조건이 빠져 갭을 놓치고,
파일 전체를 뮤테이션하면 실행 시간이 폭발한다. 선언 단위가 그 중간이다.

실측: 2줄 변경 → `extractJson` 전체(46줄)로 확장 → 뮤턴트 57개.
파일 전체를 대상으로 했다면 109개였다. **48% 감소.**

### 필터링한 것은 침묵하지 않고 보고한다

1주차에서 생존 뮤턴트의 33%가 `StringLiteral`(대부분 LLM 프롬프트 텍스트)이었다.
프롬프트 문구를 테스트로 고정하는 건 유해하므로 LLM에 넘기기 전에 잘라내되,
**몇 개를 왜 버렸는지 항상 출력한다.** 조용한 절삭은 "다 훑었다"는 착시를 만든다.

| 필터 사유 | 의미 |
|---|---|
| `noise-string-literal` | 프롬프트·상수 문자열 변이 |
| `suspected-equivalent` | 원리적으로 킬 불가능한 등가 뮤턴트 |
| `no-coverage` | 테스트가 약한 게 아니라 아예 없는 지점 (다른 문제) |
